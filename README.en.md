# a2a-hub

A multi-agent A2A coordination core. **Thin core, thick adapters**: `core/` is
platform-agnostic and open-sourceable; `adapters/` adds one pluggable layer per tool.

It solves the problem of "a pile of A2A agents each doing their own thing" —
no registry, no routing, task state lost on restart. hub fills those three gaps,
and **is itself a standard A2A agent**, so any A2A-speaking client can call it.

## What it does

| Capability | Implementation |
| --- | --- |
| **Persistence** | SQLite, six tables (tasks / messages / artifacts / contexts / agents / schema_version), WAL mode |
| **Registry & discovery** | Agent Card registry, persisted; health probing over HTTP |
| **Routing** | Select a node by agent name or capability tag (tag / skills from the Agent Card) |
| **A2A server** | Exposes Agent Card + JSON-RPC (SendMessage / **SendStreamingMessage** / GetTask / ListTasks / CancelTask) |
| **Process callback** | Downstream thinking / tool_call / tool_result / text are normalised into persisted messages |
| **Live streaming** | `SendStreamingMessage` (SSE); events are pushed **the moment they happen**, and their timestamp is the occurrence time, not the insert time |

**Core design: persist first, dispatch second.** A task is written to SQLite before
any downstream action, so if the process crashes and restarts the task state is still
queryable; a downstream failure never loses the task — it just moves it to `failed`
with the reason recorded.

## Quick start

**You do not need any real AI CLI installed.** The repo ships a zero-dependency demo
downstream (`examples/mock_agent.py`, which only uses starlette — already a hub
dependency). You can see the whole chain work in five minutes.

```bash
# 1) Install (put the virtualenv anywhere)
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -e .
```

```bash
# 2) Start a demo downstream (separate terminal)
python examples/mock_agent.py --port 9301 --name demo --tag demo

# 3) Register it
python hub.py register --name demo --endpoint http://127.0.0.1:9301 --tag demo
python hub.py agents
#   demo             a2a_http   health=unknown  tags=demo

# 4) Start the hub (another terminal)
python hub.py serve --host 127.0.0.1 --port 9200
```

Send a task (standard A2A JSON-RPC):

```bash
curl -X POST http://127.0.0.1:9200/ \
  -H "Content-Type: application/json" -H "A2A-Version: 1.0" \
  -d '{"jsonrpc":"2.0","id":"1","method":"SendMessage","params":{"message":{
        "messageId":"m1","role":"ROLE_USER",
        "parts":[{"text":"hello, hub"}],
        "contextId":"ctx-demo"}}}'
```

You get back:

```jsonc
{
  "status": { "state": "TASK_STATE_COMPLETED" },
  "artifacts": [{ "name": "response",
                  "parts": [{ "text": "[demo] echo: hello, hub" }] }]
}
```

**Now kill it and start it again** — the task is still there:

```bash
# Ctrl-C the hub, then python hub.py serve ...
curl -X POST http://127.0.0.1:9200/ -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":"1","method":"GetTask","params":{"id":"<taskId from above>"}}'
```

That is the reason hub exists: **the task is persisted before any downstream action**.
The process can crash and restart and the state is still queryable; a downstream
failure never loses the task, it just marks it `failed` with the reason.

### How to stop it

**The normal way: press `Ctrl-C` in the window running `serve`.** If you started it with
the launcher, just close that window (the server runs inside it).

hub is **not a resident service** — it is not registered as a system service and does
not auto-start, so stopping it needs no extra steps: closing the window is enough.

**If you cannot find that window** (for example it was started in the background):

```bash
# see who holds the port
netstat -ano | findstr :9200
# then stop it by PID
taskkill /PID <the-PID-above> /F
```

**What happens after you stop it** (measured):

| Item | Behaviour |
| --- | --- |
| Data already persisted | **Not lost.** The SQLite file lives at `data/hub.db`; after a restart the tasks, history and artifacts are all still there |
| Running downstream child processes | **Cleaned up together, no orphans.** The adapter puts children into a Job Object with `KILL_ON_JOB_CLOSE` — once hub dies, the job handle closes and the OS reclaims the whole process tree (including the `cmd.exe` shell and whatever it launched) |
| A task that was running | Its state stays `working`, and **the next startup settles it to `failed`** with the reason `interrupted` |
| Downstream side effects | **May already have happened.** An interrupted task does not mean it did nothing — files may already have been written into `workspace/`. The error text explicitly says to **check the workspace before re-running**, rather than trusting `ok=false` as "safe to retry" |

> Measured: dispatched a long task → hard-killed hub while it was `WORKING` → child
> process count **returned to baseline** (no orphans); after restart the task was
> `TASK_STATE_FAILED` with the reason "interrupted: hub restarted while this task was
> active… check the workspace before re-running".

## Task model

| Mode | Usage | Fits |
| --- | --- | --- |
| **Sync** (default) | `SendMessage` | Short tasks, scripting — blocks until the downstream finishes |
| **Async** | `SendMessage` + `"async": true` | Long tasks — returns a `task_id` immediately, poll with `GetTask` |

```jsonc
// Async dispatch (returns TASK_STATE_WORKING immediately)
{"jsonrpc":"2.0","id":"1","method":"SendMessage","params":{
   "agent":"dsh", "async":true,
   "message":{"messageId":"m1","role":"ROLE_USER",
              "parts":[{"text":"..."}],"contextId":"ctx-1"}}}

// Poll
{"jsonrpc":"2.0","id":"2","method":"GetTask","params":{"id":"<task_id>"}}

// Cancel
{"jsonrpc":"2.0","id":"3","method":"CancelTask","params":{"id":"<task_id>"}}
```

**Cancellation boundary**: `CancelTask` interrupts the wait on the hub side and moves
the task to `TASK_STATE_CANCELED`. For CLI agents, cancelling kills **the whole
process tree** — because a CLI is launched as `cmd.exe /c xxx.cmd`, and killing only
the shell leaves the real executable (`claude.exe` / `DeepSeek Harness.exe` …) orphaned
and still burning tokens. For HTTP agents it can only interrupt the local request;
**the downstream service keeps running** — the A2A protocol does not mandate it either,
so that side remains best-effort.

**Concurrency**: a semaphore caps how many downstream tasks run at once (default 4,
adjustable via `max_concurrency` at construction time).

**Debug endpoints**: `GET /admin/agents` (registry and capabilities),
`GET /admin/tasks` (running tasks).

## Choosing an integration path: CLI first, bridge as fallback

The same agent often supports both (DSH has both a `dsh-a2a` bridge and a `dsh` CLI).
**Prefer the CLI**:

| | CLI kind | HTTP kind (bridge) |
| --- | --- | --- |
| Resident processes | **zero** | one per agent |
| Deployment | works immediately | must start the bridge first |
| Cross-machine | ❌ local only | ✅ |
| Usable by other processes | ❌ | ✅ |

**Single machine, personal use → CLI; exposing it or crossing machines → bridge.**

The project's actual topology follows exactly that: four CLI nodes
(`claude-cli` / `codex-cli` / `dsh-cli` / `qoder-cli`), and the two HTTP bridges
(9100 / 9101) are **retired** — the CLIs connect directly, so there is no reason to
keep two extra resident processes alive.

`A2AHttpAdapter` is kept and maintained, because cross-machine scenarios need it.

## Adapters: two kinds of downstream

| Kind | Class | Talks to | Resident process |
| --- | --- | --- | --- |
| **HTTP** | `A2AHttpAdapter` | an already-running A2A service | yes |
| **CLI** | `ClaudeCLI` / `QoderCLI` / `CodexCLI` / `DshCLI` | spawns a subprocess for the CLI itself | no |

The CLI kind removes a bridge and a resident process; the cost is managing subprocess
lifecycle, timeouts and cancellation yourself.
**Single machine → CLI; cross-machine or exposed → bridge.**

## Orchestration

Three shapes are three spellings of the same mechanism:

| Shape | How |
| --- | --- |
| **Serial chain** | each step depends on the previous one |
| **Parallel fan-out** | several independent steps → same layer, in parallel; a final merge step depends on all of them |
| **Supervisor–worker** | the first layer is a supervisor step, later layers depend on it (the plan is still supplied explicitly by the caller) |

```jsonc
// Serial chain: dsh drafts → codex reviews → merge
{"jsonrpc":"2.0","id":"1","method":"RunPlan","params":{
  "contextId":"ctx-1",
  "input":"binary search",
  "steps":[
    {"id":"draft", "agent":"dsh-cli",    "prompt":"Explain {{input}} in one sentence"},
    {"id":"review","agent":"codex-cli",  "prompt":"Any factual errors?\n{{steps.draft}}"},
    {"id":"final", "prompt":"Join into one line: {{steps.draft}} | {{steps.review}}"}
  ]}}
```

**⚠️ Dependencies must be explicit — natural language does not count.**

hub only infers dependencies from `{{steps.<id>}}` template variables. Writing
"do A first, then B" in the prompt **is not recognised** — those two steps are treated
as independent and **run in parallel in the same layer**.

Two correct spellings, pick one:

```jsonc
// (1) Reference the previous step's output (recommended, most natural)
{"id": "b", "prompt": "Review this:\n{{steps.a}}"}

// (2) Declare the dependency explicitly (for "ordered but does not consume output")
{"id": "b", "dependsOn": ["a"], "prompt": "Copy the artifact to backup/"}
```

Symptoms of a missing dependency: parallel execution, template variables resolving to
nothing, or consuming an unfinished upstream result.

**Automatic inference**: writing `{{steps.draft}}` automatically adds
`dependsOn: draft` — no need to write it twice (omitting it causes same-layer
parallelism and empty template variables). Explicit `dependsOn` is still supported,
for the "ordered but does not consume output" case.

**Failure policy**: `fail-fast` by default (one step fails, the whole chain stops),
overridable per step:

```jsonc
{"id":"flaky", "agent":"dsh-cli", "prompt":"...", "onError":"continue"}
```

With `onError: continue`, **independent branches keep running** after that step fails;
only downstream steps that depend on it are blocked.

**Execution model**: topological layering → same-layer parallelism (`asyncio.gather`)
→ advance layer by layer. Every step is persisted as a task carrying `planId` /
`stepId`, so `GetPlan` can reconstruct the whole plan afterwards.

**A2A compatibility**: orchestration is not an A2A protocol concept; `RunPlan` /
`GetPlan` are **extension methods** — they do not affect the standard methods, and a
pure A2A client can be completely unaware of them.

## Unified audit

One top-level request (`SendMessage` or `RunPlan`) shares a single **`traceId`**,
threading every task and message it caused into one traceable chain.

**Interfaces**:

| Way | Purpose |
| --- | --- |
| `GetTrace` (JSON-RPC) | Structured data: summary / tasks / timeline |
| `ListTraces` (JSON-RPC) | Recent trace overview list |
| `GET /admin/trace/<traceId>` | Human-readable timeline view |
| `GET /admin/traces` | Same, as a list |

**Three sections of output**:

| Section | Contents |
| --- | --- |
| `summary` | Start/end, total elapsed, which agents were involved, **normalised aggregate usage** |
| `tasks` | Every task under this request (plan steps, parent/child links, per-task duration) |
| `timeline` | All message events flattened by time — a complete reconstruction of the process callback |

```
$ curl http://127.0.0.1:9200/admin/trace/trace-b04456c0158a
trace trace-b04456c0158a
  agents  : claude-cli, codex-cli, dsh-cli
  tasks   : 3 (ok 3 / fail 0 / cancel 0)
  elapsed : 20449 ms
  usage   : {"input": 37735, "output": 633, "cacheRead": 19328, "total": 38368}

  tasks:
    [completed] a      dsh-cli      3705ms   Explain quicksort in one sentence
    [completed] b      codex-cli   15037ms   Key points for a minimal runnable example
    [completed] merge  claude-cli   5380ms   Merge the two passages below…

  timeline:
    03:26:15.923  dsh-cli     text      Explain quicksort in one sentence
    03:26:19.599  dsh-cli     thinking  The user asks for a one-sentence explanation…
    03:26:19.603  dsh-cli     text      Quicksort: pick a pivot from the sequence…
    03:26:30.963  codex-cli   status    turn started
```

**Parallelism is visible straight from the timeline**: `dsh-cli` and `codex-cli`
both start at `03:26:15`.

**Usage normalisation**: downstream usage field names differ
(`inputTokens` / `input_tokens` / `prompt_tokens` …), so they are normalised to
`input` / `output` / `cacheRead` / `cacheWrite` / `reasoning` / `total` before
aggregation. **A downstream's self-reported `total` is discarded** — it is that
call's own sum, and adding it would produce a number that is neither a total nor a
component; `total` is always recomputed as `input + output` by the aggregator.

## Authentication

Enable it (off by default, which is enough when bound to loopback):

```bash
python hub.py serve --token <your-token>     # or export HUB_TOKEN=<your-token>
```

**The public surface is deliberately minimal**:

| Path | Auth required | Why |
| --- | --- | --- |
| `/.well-known/agent-card.json` | public | The A2A spec requires the card to be publicly discoverable |
| `/healthz` | public | Monitoring / load-balancer probe |
| `/console` | public | Just an HTML shell with no data; the `/admin/*` it calls still requires auth |
| Everything else (all `/admin/*` and JSON-RPC) | **required** | `Authorization: Bearer <token>` |

Failures return 401 + `WWW-Authenticate: Bearer`. Token comparison uses
`hmac.compare_digest` (constant-time).

## Letting any agent platform call the hub

Platforms do not agree on extension mechanisms: WorkBuddy / DSH use **skills**,
Codex / Qoder / Claude Code use **MCP**. But **all of them support an MCP client** —
so one MCP facade covers every platform, instead of writing a skill per platform.

### MCP facade (optional component)

```
mcp_facade/           # independent of core; delete it and hub is still complete
└── server.py         # talks to hub over HTTP (does not import core), so it starts/stops separately
```

It exposes six tools:

| Tool | Purpose |
| --- | --- |
| `hub_status` | Health check: task count / node count / running |
| `hub_agents` | List registered agents (name / kind / health / capability tags) |
| `hub_send` | Dispatch a task (by agent or tag routing, supports `context_id` continuation) |
| `hub_plan` | Run a multi-agent orchestration pipeline (steps array) |
| `hub_trace` | Query the cross-agent audit timeline |
| `hub_tasks` | Recent task list |

**Design boundary**: it is an **integration form**, not the core. `core/` stays pure
A2A and unchanged; the facade talks to hub over HTTP, so the two are decoupled —
swap the facade out and hub is still a complete A2A service.

## Live streaming (SSE)

hub implements A2A's `SendStreamingMessage`, and the Agent Card honestly declares
`capabilities.streaming = true`.

```bash
curl -N -X POST http://127.0.0.1:9200/ \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":"1","method":"SendStreamingMessage",
       "params":{"agent":"dsh-cli",
                 "message":{"messageId":"m1","role":"ROLE_USER",
                            "parts":[{"text":"look up xxx for me"}]}}}'
```

The event body is a **standard A2A `StreamResponse`** (`statusUpdate` / `task`), so a
pure A2A client can parse it without knowing any extension:

```
data: {"jsonrpc":"2.0","id":"1","result":{"statusUpdate":{...state=working...}}}
data: {"jsonrpc":"2.0","id":"1","result":{"statusUpdate":{...one process event...}}}
data: {"jsonrpc":"2.0","id":"1","result":{"task":{...terminal state + artifacts...}}}
```

**Why this deserves its own section**: process events used to be written to the
database in a batch **after `adapter.call` finished**, so every timestamp was the
insert time — a task that really ran for 181 seconds had all of its process events
crammed into a 64-millisecond window. The console rendered that as a "timeline":
**honest declaration, misleading presentation**. Now events go out **the moment they
happen** and the timestamps are occurrence times, so the ordering is real.

Three design trade-offs:

| Trade-off | Why |
| --- | --- |
| Payload is a standard `StreamResponse`, with process-event semantics in `metadata.kind` | A2A has no "thinking / tool_call" type; the closest carrier is `status.message`. This way **a client that does not know about us can still display it as a progress message** |
| Subscriber queue is **bounded**; when full, drop the oldest and count it | A slow client (a frozen browser tab) must never be able to stall a running task. The drop count travels with the stream so the client can mark the gap instead of being silently misled |
| Heartbeat as an SSE comment line (`: keep-alive`) | An agent thinking for minutes is normal; without a heartbeat intermediaries cut the connection. A comment line does not pollute the data |

Passing `taskId` without `message` means **attaching to a task already running**:
replay history first, then follow live. That is what lets the console reconnect after
a page refresh.

### Parallelism analysis

"Total elapsed" cannot tell you whether parallelism actually took effect. The trace
detail gives you these numbers:

| Metric | How to read it |
| --- | --- |
| **Average parallelism** | Total serial time ÷ wall clock. **1.0 = fully serial**, N = on average N agents were working at once |
| **Peak parallelism** | The most agents working simultaneously |
| **Idle ratio** | Share of the wall clock during which no agent was working — a high value usually means waiting on a lock or on the previous layer finishing |
| **Orchestration overhead** | How much the wall clock exceeds the "theoretical minimum" — **this is the answer to "can it go faster"** |
| Utilisation timeline | How many agents were working in each time slice; hugging the baseline = nobody working |

**Layering is inferred from observation**, with a single criterion:

> **The batch that starts only after the previous batch has fully finished is a new
> layer.**

That is the *definition* of strict layering (the orchestrator makes layer N+1 wait for
layer N to finish completely), so it depends on no empirical threshold.

> This was **settled only after getting it wrong twice**. The first version used "start
> times more than 50 ms apart", and it failed in both directions:
>
> - Threshold too large relative to the layer: the demo downstream (mock) finishes a
>   whole layer in milliseconds → **a 2-layer plan was reported as 1 layer**
> - Threshold too small relative to dispatch spacing: the HTTP adapter dispatches the
>   three tasks of one layer ~45 ms apart, so the third is 89 ms from the layer start →
>   **three genuinely overlapping parallel tasks were split into 2 + 1 layers**
>
> The shift in perspective: **"how far apart are the start times" is simply the wrong
> question**. "Do the intervals overlap" is the right one. **Two tasks whose time
> intervals overlap are in the same layer, by definition.**

The theoretical minimum is the sum of each layer's "slowest task".

**The one cost**: if tasks in a layer get serialised by the concurrency cap (one starts
only after the previous finishes), they are reported as separate layers. But that is
the truth — at that moment they really were not running in parallel, and the metric
should say so.

> **This is a lower bound for the layering, not a strict critical path** — a strict
> critical path needs the dependency graph from the plan, which is not persisted. So
> these numbers answer "did parallelism take effect, and how much time is idle",
> not "the exact shortest possible duration". The methodology is stated in the return
> value (`layerSource`) and on the console panel.

**Measured** (four-node orchestration, the 2026-10-06 run): average parallelism 1.48×,
peak 2, idle ratio 0, orchestration overhead 2 ms — layer 0 ran two agents in parallel
(1.84× speed-up), layer 1 merged.

The Live view reads SSE with `fetch` + `ReadableStream` rather than `EventSource`:
the latter can only issue GET, so it cannot carry a message body.

**Capability boundary**: read-only plus triggering health probes. It does not
enable/disable agents or cancel tasks — once the console can write, it needs
authentication, which is a different order of magnitude of work.

| Form | Size | Files | Ready after | Notes |
| --- | --- | --- | --- | --- |
| **onedir** | 26.7 MB | 75 | **0.34 s** | Fast start, easy to diagnose. **Recommended** |
| onefile | 12.4 MB | 1 | 1.47 s | Easy to copy, but extracts to a temp directory on every start |

(Measured on Windows 11 + Python 3.13; `--both` builds both and starts each one to
hit `/healthz`.)

**Data follows the exe**: `data/hub.db` and `workspace/` sit next to the exe. Copy the
exe anywhere and the data goes with it — exactly the semantics a portable app should
have.

### Double-click launch: `start-hub.bat`

**Double-clicking `a2a-hub.exe` does not work** — with no subcommand it just prints a
usage error and exits (exit code 2). The build places a `start-hub.bat` next to the
exe, so **double-click that instead**:

```
a2a-hub/
├── a2a-hub.exe
├── start-hub.bat     ← double-click this
└── _internal/
```

What it does: start the server → wait until it is ready → open the browser at
`/console`. The server runs in its own window, so **the log stays visible and Ctrl-C
stops it**.

```bat
start-hub.bat          :: default port 9200
start-hub.bat 9300     :: use another port
```

**It finds the exe itself.** It checks these in order and uses the first hit:

1. Next to the script (the normal case — that is how the build lays it out)
2. `dist\a2a-hub\a2a-hub.exe` next to the script
3. `dist\a2a-hub\a2a-hub.exe` and `dist\a2a-hub.exe` one level up

So **`packaging\start-hub.bat` works from a source checkout too** (it finds the
build output under `..\dist\`). When nothing is found it **lists every path it
tried** and gives two concrete fixes, instead of just saying "not found".

Once located, it `cd`s to the exe's folder before launching — because `data\` and
`workspace\` follow the exe, which is what makes "copy the whole folder anywhere"
actually hold.

> **This .bat is deliberately ASCII-only.** cmd.exe parses .bat files using the
> **system code page** (GBK/cp936 on Chinese Windows), so a UTF-8 batch file with
> non-ASCII text turns into mojibake — and worse, a truncated multi-byte sequence can
> break the parser and produce baffling errors. Putting `chcp 65001` at the top does
> not save you: cmd has already started reading the file by then. The rest of the repo
> is UTF-8; this one file is a deliberate exception (`.gitattributes` declares
> `*.bat text eol=crlf`, because cmd needs CRLF line endings).

### Restricted directories: an environment pitfall for onefile

**If the exe is placed in a directory restricted by security policy, onefile fails to
start**:

```
[PYI-1234:ERROR] Could not create temporary directory!
```

onefile extracts itself to a temp directory on startup. If the process's **image lives
in a restricted directory** (measured: some sandboxes downgrade the token of processes
in certain directories), that step is refused.

**This is not a packaging defect** — the way to tell: copy the same exe elsewhere and
it runs, or put a hello-world onefile build in the same directory and it **fails the
same way**.

The onedir build is **unaffected** (it does not need to create a temp directory), so
**use onedir when you are unsure about the environment**.

### Restricted directories: it also affects "hub dispatching to downstream" — onedir is not immune either

The same token-downgrade mechanism has a second consequence, and **onedir hits it too**:

An exe in a restricted directory fails to spawn some downstream CLIs. Measured:
**dsh-cli returns exit code 1**, while the same exe copied to an unrestricted directory
works; claude / codex / qoder are **unaffected**.

Two other symptoms of a restricted process in the same environment (useful to confirm
it is downgrading rather than misconfiguration):

- It cannot even write to `%TEMP%` (`sqlite3.OperationalError: unable to open database
  file`), but **it can write to its own directory** — which is why `data/` next to the
  exe works
- Clearing `NODE_OPTIONS` / `PYTHONPATH` **does not help**, so it is not env leakage

**What to do**: run the exe from an ordinary directory (not one restricted by policy).
If it must live in a restricted location, whitelist that directory in your security
software.

Two packaging pitfalls that were hit and **have been fixed** (both documented in code
comments):

- **Do not use `__file__` to locate the data directory once frozen.** PyInstaller puts
  the code inside the bundle, and in onefile mode that is a **temp directory deleted on
  exit** — putting the database there means starting from zero on every restart, and
  losing it **silently**. When frozen, the exe's own directory is used now.
- **A frozen exe does not honour `PYTHONUTF8` / `PYTHONIOENCODING`.** It works fine on
  a dev machine (because the env vars are set there), but when a user double-clicks it
  the Chinese text is mojibake — measured: `(来自 Agent Card)` came out as
  `(\xc0\xb4\xd7\xd4 Agent Card)`. `hub.py` now pins stdout/stderr to UTF-8 explicitly,
  independent of the environment.

> **uvicorn's dynamic imports**: its loop / protocol implementations are imported by
> **string** (`uvicorn.loops.auto` → `uvicorn.loops.asyncio`), which static analysis
> cannot see. `packaging/hub.spec` uses `collect_submodules("uvicorn")` to collect them
> all at once — enumerating them by hand is a bet that you missed none, and you only
> find out at runtime.

## Repository layout

The repo can be used standalone and open-sourced as-is — the code layer contains no
machine paths, credentials or runtime data. The places marked "**runtime**" below are
excluded by `.gitignore`; for why they are split this way and how to move to a new
machine, see [`docs/architecture.md`](docs/architecture.md).

```
a2a-hub/
├── core/                  platform-agnostic, open-sourceable
│   ├── store.py           SQLite six tables + schema migration + transaction boundaries + queries
│   ├── registry.py        Agent registry + health probing
│   ├── router.py          Capability-matching routing
│   ├── orchestrator.py    Orchestration engine (topological layering + same-layer parallelism + templates)
│   ├── hub_app.py         The A2A server (incl. RunPlan / GetPlan extensions + admin endpoints)
│   └── console.py         Read-only console (single-page HTML, zero front-end deps)
├── adapters/              one layer per downstream, pluggable
│   ├── base.py            Adapter contract + downstream normalisation
│   ├── a2a_http.py        Generic HTTP A2A adapter (raw JSON-RPC, zero SDK dependency)
│   └── cli.py             CLI adapters (claude / qodercli / codex / dsh)
├── mcp_facade/            **optional component**: wraps hub as an MCP server
├── examples/
│   ├── mock_agent.py      Zero-dependency demo downstream (what Quick start uses)
│   ├── agents/            Registration samples for four real CLIs
│   ├── mcp/               MCP integration samples per platform
│   └── plan-*.json        Orchestration definition samples
├── docs/
│   ├── architecture.md    Architecture (layering / data flow / extension points)
│   └── adr/               Architecture decision records (why it is this way)
├── tools/
│   └── run_plan.py        Long-orchestration submitter (configurable timeout, results to disk)
├── probes/
│   └── process_monitor.py Local AI tool process probing (the adapter `detect` implementation)
├── tests/                 Three-tier self-check: unit / platform / integration
├── hub.py                 Command-line entry point
├── agents/                Local agent registration configs (**runtime**, not in the repo)
└── data/hub.db            SQLite (**runtime**, not in the repo)
```

**A new execution backend = a new `Adapter` subclass, with zero changes to core.**
That is what "thick adapters" means.

## Two pitfalls you must know

Both from real measurement, and **you will hit both from the command line and when
writing an adapter**:

1. **Local probes must bypass the system proxy.** If the machine has a system proxy,
   requests to `127.0.0.1` get intercepted and return **502** (not connection refused),
   which is very easy to misread as "the service is running but erroring". Add
   `--noproxy '*'` on the command line, and use `trust_env=False` in code.
2. **Do not reuse one keep-alive connection for fetching the Agent Card and sending
   JSON-RPC.** Some A2A implementations reliably return 404 when you GET then POST on
   the same connection.

## Known boundaries

Listed honestly, so you do not have to discover them the hard way:

- **Windows only.** The interfaces are platform-agnostic, but the Job Object,
  `cmd.exe` wrapping and `taskkill` fallback have only been verified on Windows. The
  CLI adapters are untested off Windows.
- **Streaming is implemented, but downstream differences show up in timestamp
  precision.** For CLI downstreams over `SendStreamingMessage` (SSE) the timestamps
  are **true occurrence times**; HTTP downstreams are polled, so the timestamp can only
  be "the moment this poll picked it up", limited by the polling interval. Tasks run
  before this version have batch-write timestamps and **must not be used to analyse
  ordering**.
- **`RunPlan` blocks synchronously.** A long orchestration will exceed the client
  timeout, and then you get neither the result nor the `planId`. Use
  `tools/run_plan.py` (configurable timeout, results written to disk).
- **Write capability varies per node and cannot be declared.** codex-cli is a read-only
  sandbox, qoder-cli waits for someone to click authorise (a subprocess started by hub
  has no TTY), claude-cli / dsh-cli can write. Do not count on the first two when you
  need files produced.
- **`hub → WorkBuddy` is not connected**, and that is a design boundary rather than a
  defect: that platform only exposes a tool set, with no task-level entry point. The
  reverse direction (WorkBuddy → hub) works.
- **It is a service, not a library you import.** The distribution name is `a2a-hub`
  while the importable top-level modules are `hub` / `core` / `adapters` / `probes` /
  `mcp_facade`. Generic names like `core` and `adapters` occupy the top level of
  site-packages — if you want to use it as a library, install it into a dedicated
  virtual environment (which is what the Quick start does).
- **Not done yet**: CI runs only the unit + platform tiers; no PyPI release; no Docker.
