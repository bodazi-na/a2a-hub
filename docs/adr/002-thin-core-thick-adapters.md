# ADR-002：薄核心 + 厚适配器，CLI 优先、桥为备选

## 状态

已采纳（2026-10-06）

## 背景

要纳管的 6 个工具，接入形态差异极大：

- **CLI 类**：`claude -p` / `codex exec` / `qodercli -p` / `dsh --profile headless`
- **HTTP 类**：早期自建的两条 A2A 桥（`codex-a2a` / `dsh-a2a`，常驻进程）
- **无入口类**：Claude Desktop（MSIX 闭源 GUI）；WorkBuddy 只暴露工具集、无任务级入口

一个绕不开的判断：**Electron 应用能不能接入？**

早期直觉是「Electron = 不能接」，但这条判断是错的 —— DeepSeek Harness 就是
Electron 应用，却带着完整的 headless CLI。

## 决策

**两条一起定：**

1. **架构分两层**：`core/` 平台无关；`adapters/` 每个工具一层。
   新增一种执行体 = 新增一个 `Adapter` 子类，**core 一行不改**。
2. **接入方式 CLI 优先，HTTP 桥为备选**。默认走 CLI 直连（直接起子进程），
   只有「跨机器」或「对外暴露」才起桥。

## 理由

**为什么分层**：差异必须被吃掉在一处。core 里任何一句「如果是 codex 就……」都是
架构腐化的开始 —— 它会让「加一个工具」从「写一个文件」变成「改五处」。

**为什么 CLI 优先**：

| | CLI 直连 | HTTP 桥 |
| --- | --- | --- |
| 常驻进程 | 无 | 需要（每个工具一个） |
| 额外端口 | 无 | 每个工具一个 |
| 故障面 | 只有子进程 | 子进程 + 桥进程 + 网络 |
| 跨机器 | 不支持 | 支持 |
| 复用下游会话 | 靠 CLI 自己的 session 机制 | 同左 |

单机自用时，桥的每一层都是纯粹的额外成本。本机四个 CLI 全部实测打通后，
两条桥就退役了。

**为什么保留 `A2AHttpAdapter`**：它没有为那两条桥写任何特化代码 ——
任何符合 A2A 的服务注册即可用。这是「薄核心」的直接收益，
所以即便自用不走它，也不该删。

**关于「Electron 能不能接」**：判断标准不是「是不是 Electron」，
而是**「有没有 headless 入口」**。这个教训值得单独记 ——
按技术栈判断可行性，很容易把能做的事误判成不能做。

## 后果

**变容易的**：

- 加新工具是纯增量：写一个 `Adapter` 子类 + 一个 `examples/agents/*.json`
- 测试可以按「是否需要本机环境」分组，而这个分界线**恰好就是架构边界** ——
  单元级全绿 ⟺ core 确实与平台无关。CI 因此同时是**架构约束的自动验证器**
- 对外暴露时不用改 core，换个 adapter 就行

**变难的**：

- CLI 适配器要自己管子进程生命周期：超时、取消、进程树回收、输出流解析。
  这些是 HTTP 适配器完全不用操心的（ADR-004、ADR-005 都源于此）
- 每个 CLI 的输出格式不同，解析逻辑要一家一份（虽然 claude / qodercli 可以共用）
