# ADR-003：持久化用 WAL + `synchronous=NORMAL`

## 状态

已采纳（2026-10-06）

## 背景

一次真实负载演练（用 hub 审 hub）暴露出：**一个产生 50 个过程事件的任务，
会把事件循环硬阻塞 193 毫秒** —— 这期间 `CancelTask` 和所有其它请求都调度不了。

实测数据：

| 项 | 值 |
| --- | --- |
| 单次 `add_message` | **4.57 ms** |
| 写 50 个事件 | 262 ms（事件循环最大阻塞 257 ms） |
| PRAGMA | `journal_mode=wal`、**`synchronous=2`（FULL）**、`busy_timeout=5000` |

根因不是「同步 API」，是 **`synchronous=FULL` 让每次 COMMIT 都 fsync**。

## 决策

**`PRAGMA synchronous=NORMAL`**（SQLite 官方对 WAL 模式的推荐值），
配合**单事务批量写入**（`Store.add_messages()`）。

## 理由

对照实验（50 次写入）：

| 设置 | 写入耗时 | 事件循环最大阻塞 |
| --- | --- | --- |
| `synchronous=FULL`（原状） | 197.7 ms | **192.8 ms** |
| `synchronous=NORMAL` | 3.1 ms | 10.8 ms |
| `NORMAL` + 单事务批量 | **0.9 ms** | 11.9 ms |

**64 倍 / 220 倍。**

**语义差别（SQLite 文档明确说明）**：

- WAL + NORMAL **不会因进程崩溃而损坏或丢失已提交数据**
- 只有**操作系统崩溃 / 断电**才可能丢掉最近若干个事务

对「任务协调日志」这个用途，取舍是划算的：

1. **进程被杀是最常见的崩溃形态**，这种情况不丢数据
2. 断电场景由启动时的 `recover_orphans` 兜住 —— 它会把残留的活跃任务结算成
   `failed` 并提示「可能已产生副作用」，**不会留下卡在 `working` 的任务**

**为什么还要批量**：`_execute` 会把一个任务的过程事件逐条落库。即便 NORMAL 下
每次 COMMIT 只要 ~0.06ms，50 次仍然是 50 次系统调用。合成一个事务后 fsync
只发生一次，顺带把「50 个事件」变成一个原子操作。

## 后果

**变容易的**：

- 写密集路径（过程回传）不再阻塞服务
- 批量写入天然是原子的 —— 要么全写要么全不写

**变难的 / 需要接受的**：

- **断电可能丢最近若干事务**。这是显式的取舍，不是意外
- 用 `synchronous=NORMAL` 意味着不能拿这个库当「金融级账本」用。
  它是**协调日志**，不是账本

**防退化**：新增 `tests/test_store_blocking.py`，主力是**结构性断言**
（PRAGMA 值必须是 NORMAL、批量只开一个事务、逐条调用次数不随事件数增长），
计时只做兜底。结构性断言不受机器快慢影响，在 CI 上可靠。
