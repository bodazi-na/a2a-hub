# ADR-005：**不**把 Store 改造成 `asyncio.to_thread`

## 状态

已采纳（2026-10-06）—— 这是一个**「决定不做什么」**的记录

## 背景

一次真实负载演练的外部审查报告里，针对「`Store` 阻塞事件循环」给出了明确建议：

> store 调用改走 `asyncio.to_thread`（或专用单写线程），退避改为调用侧
> `await asyncio.sleep`，事务内不做同步 sleep。

问题是真实的（见 ADR-003 的实测数据：写 50 个事件阻塞事件循环 193ms）。
建议的方向在原则上也对 —— `Store` 是同步 API，却全在事件循环线程上被调用。

**但我先量了一下，然后没有采纳。**

## 决策

用两层**局部**改动解决问题，**不引入线程**：

1. `PRAGMA synchronous=NORMAL`（ADR-003）
2. `Store.add_messages()` 单事务批量写入

实测结果：**193ms → 0.9ms（约 200 倍）**，残余阻塞与测量本身的噪声同量级。

## 理由

**① 收益已经被吃掉了。** 对照实验：

| 设置 | 事件循环最大阻塞 |
| --- | --- |
| `synchronous=FULL`（原状） | 192.8 ms |
| `synchronous=NORMAL` | 10.8 ms |
| `NORMAL` + 单事务批量 | 11.9 ms |

根因不是「同步 API」，是**一次 fsync**。改一个 PRAGMA 就拿到 64 倍 ——
而按原建议做大重构，收益不会比这更好。

**② 重构会引入新的竞态风险。** 把 store 调用改成 `await`，等于在
`_execute` 里给「更新状态 → 写消息 → 写产物」之间**插入新的可被打断点**。
现在这些调用是**同步的，因此在事件循环上原子** —— 别的协程插不进来。
改成 `to_thread` 后，两个并发任务可以在这些点之间交错，而 `only_from` 的
原子状态保护只覆盖单条 SQL，不覆盖「三条语句的组合」。

**③ 重构成交面大。** `Store` 被 `hub_app` / `orchestrator` / `registry` /
`router` / `tests` 全面直接调用。改成 async 要么全改（大 diff、大风险），
要么两套 API 并存（更容易用错）。

**权衡结论**：拿一个「已经用 20 行拿到 200 倍」的改动，去换一个
「几十处调用点 + 新增竞态面」的重构 —— 不划算。

## 后果

**接受的**：

- `Store` 仍然是同步 API。**新增的 store 调用仍然会阻塞事件循环** ——
  只是单次代价从 4.57ms 降到约 0.06ms 量级
- 如果将来出现「单次操作就 ms 级」的新查询（比如全表扫描、大 payload 序列化），
  这个决策需要重新评估

**得到的**：

- **防退化测试**（`tests/test_store_blocking.py`）把结论钉住了：
  三条结构性断言（PRAGMA 值、批量只开一个事务、逐条调用次数不随事件数增长）
  + 一条计时兜底。谁把 `synchronous` 改回 FULL、或把批量改回逐条，CI 会红

## 这个 ADR 想说的

**「改用线程 / 改异步」常常不是性能问题的正解。** 这次的真实根因是一次
fsync —— 一个配置项。**测量的成本是几分钟，重构的成本是几天**，
而先测量还顺带排除了「重构完发现收益差不多、却多了一堆竞态」的坏结局。

所以流程应该是：**先测量定位根因 → 再决定改哪儿**，而不是拿到「这里阻塞了」
就直接上最重的方案。
