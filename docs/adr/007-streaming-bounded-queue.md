# ADR-007：实时流用「有界队列 + 丢最老」做背压

## 状态

已采纳（2026-10-07）

## 背景

实现 `SendStreamingMessage`（SSE）时，任务执行协程需要把过程事件推给
订阅者（控制台 / 其它 A2A 客户端）。天真的做法是给每个订阅者一个
`asyncio.Queue()`（无界）或直接 `await queue.put(...)`。

两种做法各有一个致命问题：

| 做法 | 问题 |
| --- | --- |
| `await queue.put()`（无界等待） | 订阅者读得慢（浏览器卡住、断网但连接没断）→ 队列永远不满 → **生产者被拖住**，而生产者正是「正在跑下游 CLI 的那条协程」。一个看热闹的客户端能拖慢整个任务 |
| 无界 `Queue()` | 不阻塞，但订阅者若一直不读，事件在内存里**无界增长**。一个僵死连接就能把 hub 撑爆 |

两者都不可接受。这不是理论问题：任务动辄跑几分钟、产生几十到几百条事件。

## 决策

**每个订阅者一个有界队列（`SSE_QUEUE_MAX = 256`）；满时丢最老的，让最新的
总能进来，并累计 `dropped` 计数。**

`_publish()` 保证**绝不阻塞、绝不抛异常** —— 它跑在任务执行的关键路径上。
`dropped` 随流送出去（放进 `statusUpdate.metadata`），控制台据此标出断点。

## 理由

**为什么丢最老而不是丢最新**：客户端看的是「现在在干什么」。
丢掉最老的、保住最新的，最坏情况是漏掉一段历史；反过来则是
「一直在补很久以前的事，永远追不上现在」。

**为什么把 `dropped` 送出去**：静默丢数据是这里最危险的失败模式 ——
控制台会显示一条连续的流，读者以为它是完整的。带上计数，客户端就能
如实标出「中间丢了 N 条」，把「不完整」变成**可见的**不完整。

**为什么不做流控（backpressure 反压）**：反压意味着让生产者等消费者，
但这里的生产者是任务执行本身。让「看的人」有权力拖慢「干活的人」，
在一个协调内核里是错的优先级。

**为什么不用无界队列 + 定期清理**：清理策略需要判断「这个订阅者是不是
真的死了」，而 TCP 半开连接恰恰最难判断。有界队列让内存占用有个硬上界，
不依赖任何活性判断。

## 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| `await queue.put()` | 慢客户端会拖住任务执行。不可接受 |
| 无界 `asyncio.Queue()` | 僵死连接导致内存无界增长 |
| 有界 + `put_nowait` 失败就**丢当前这条** | 慢客户端会永久停留在「很久以前」的状态，越落越远 |
| 有界 + 断开慢订阅者 | 需要判断「多慢算慢」，阈值是拍脑袋的；而且断开会丢光后续事件，比丢中间一段更糟 |
| 把事件先落库、客户端轮询 `GetTask` | 这正是**改造前**的状态。它的问题是：轮询间隔决定延迟，且事件时间戳只能是落库时刻 —— 时序信息永久丢失（N5） |

## 后果

- 慢客户端只影响自己，任务照常跑完。有回归测试锁住
  （`tests/test_streaming.py::test_slow_subscriber_does_not_block_task`）
- 客户端**可能收到不完整的流**。这是显式的取舍，代价由 `dropped` 计数
  补偿 —— 不完整但**可知**
- 256 这个值覆盖「客户端卡一下」的抖动（一次工具调用爆发式产生几十条事件），
  又不至于让单个僵死连接囤积无界内存
- 订阅是**进程内**的，不做持久化。重启丢订阅是对的 —— 持久化由 `store` 负责，
  总线只服务「同一时刻正在看的人」。想补历史用 `GetTask` 或带 `taskId` 接入
