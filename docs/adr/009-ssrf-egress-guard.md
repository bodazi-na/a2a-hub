# ADR-009：定向 SSRF 防护 —— 拦内网，放行回环

## 状态

已采纳（2026-10-12）

## 背景

hub 对下游 agent 的地址**不是自己决定的**，有两个来源：

1. `register --endpoint URL` —— 运维填的；
2. **下游 Agent Card 里的 `supportedInterfaces[].url`** —— **下游自己填的**。

第 2 条是问题所在。`A2AHttpAdapter._pick_rpc_url()` 原本**直接采信**卡片声明的
JSON-RPC 端点，随后 `probe` 与每次派活都会往那个地址发请求，响应体还会被
`resp.json()` 解析回传。

于是「注册一个恶意 / 被投毒的 A2A 下游」≈「拿到一条对内网任意端点发 POST 的通道」。
落到云主机上，`169.254.169.254`（链路本地地址）就是实例凭据端点。hub 的定位是
「本机工具」，不该顺手变成一个内网跳板。

这不是理论风险 —— 是**代码里现成的路径**，无需任何越权即可触发。

## 决策

1. 新增 `core/netguard.py`，统一负责出网目标的判定与拦截。
2. **默认拦**：链路本地（含云元数据）、私网（RFC1918 + CGNAT）、保留段、组播、非 http(s)。
3. **默认放行**：回环、公网、域名（判定推迟到连接层）。
4. 拦截点在 **`httpcore` 网络后端**（`_GuardedNetworkBackend`），不是只在入口预检。
5. 放宽开关只有一个：`--allow-local-targets`。
   注意它**只额外放开私网** —— 回环默认就是放行的，这个开关名字里带
   「local」是为了贴合用户心智（「允许内网目标」），实现上只改一个旋钮。
   **链路本地没有开关。**

## 理由

### 为什么拦内网

SSRF 的额外能力来自**越过网络边界** —— 打到调用方自己够不着的内网与控制面。
这正是 hub 最不该提供的：它已经能驱动本机 CLI agent 执行代码，
再叠加一条内网通道，等于把「本地工具」升级成「内网跳板」。

### 为什么**不**拦回环（这是本决策最反直觉的地方）

教科书式 SSRF 防护会连回环一起拦。这里刻意不拦，因为**hub 的全部既有用法
都是回环**：本机桥接服务、本机 mock、`127.0.0.1:9100/9101`。

一刀拦掉的后果不是「更安全」，而是**砍掉主场景** —— 而一个砍掉主用法的默认值，
最后一定会被使用者用某个 `--allow-*` 整体关掉，连带真正该拦的一起放行。
**能长期开着的默认值，比理论上更严的默认值有用。**

需要更严的场景（hub 只与远端 agent 通信）可以用
`TargetPolicy(allow_loopback=False)` 关掉。

### 为什么不拦公网

公网目标没有「越过边界」这个加成 —— 能注册 agent 的人本来就能直连它。
拦它只会误伤「把 hub 指向远端的另一个 hub」这种正常用法。

### 为什么在连接层，而不是只在入口预检

`_pick_rpc_url()` 是「**先拉卡片、再按卡片内容请求**」—— 最终请求目标运行时
才确定，入口预检根本看不到它。

把判定放进拨号那一刻还有第二个收益：**查到的是本次连接实际要拨的地址**，
DNS rebinding（预检解析到公网、连接时解析到内网）随之失效。

### 为什么解析要自己做

踩过一次坑：原以为「连接层的 host 参数就是解析后的 IP」—— **不是**。
`httpcore` 把域名原样交给后端，解析发生在后端内部。实测
`make_client().get("http://localhost:9/")` 时，护栏后端收到的 `host` 是字符串
`'localhost'`，而不是 `127.0.0.1`。而判定函数对域名一律返回「放行」，
于是**解析到内网的域名畅通无阻** —— 防护形同虚设。

现在显式做「解析 → 对**每个**结果过护栏」。**刻意不只查第一个地址**：
一个域名可以同时解析出公网与内网地址，只查第一个等于给攻击者留一个
「把内网地址排在后面」的机会。

## 后果

**好处**

- 「注册恶意下游」不再等于「获得内网 POST 通道」
- 云元数据端点默认不可达 —— hub 不会被用来窃取实例凭据
- 域名形式的 rebinding 也被覆盖（连接层解析后判定）
- 主场景（本机下游）零改动即可继续工作

**代价**

- **本机非回环的内网下游需要显式开关**：如 `192.168.x.x` 上的 agent
  要加 `--allow-local-targets`。这是刻意的摩擦 —— 让「连内网」成为一个
  需要说出口的决定，而不是默认行为
- 多了一次 DNS 解析（仅域名目标；IP 字面量直接判）。对本地桥接场景无影响
- `GuardedTransport` 依赖 `httpx` 的 `_pool._network_backend` 这一**内部结构**。
  它变了就必须改。**取不到时直接抛异常，不静默降级** ——
  「以为有护栏、实际裸奔」比起不来更危险

**验证方式（实测，非推断）**

- `tests/test_ssrf_guard.py` **71 项断言**：含「必须拦」与「必须放行」两组
  **对照面**（只有拦没有放行的测试，无法区分「护栏正确」和「护栏拦一切」）
- 连接层用例走**真实 client**，不走 transport 内部方法 ——
  第一版护栏重写了 `httpx.AsyncHTTPTransport.connect_tcp()`，
  而 **httpx 0.28 根本没有这个方法**（只有 `handle_async_request` / `aclose`），
  那个重写是死代码。直连内部方法的测试测不出这个问题：
  IP 字面量因为入口预检仍被拦，看起来「管用」，而域名目标会溜到真正建连
- 全档 16 项 + 集成档（真实 CLI / hub 在跑）

## 已知局限（写在文档里，不假装没有）

- **不比 `is_private` 更全**：显式网段表覆盖了 RFC1918 / CGNAT / 链路本地 /
  保留段 / 组播，但**不覆盖所有私有用途网段**（如某些运营商内部段）。
  这是刻意的取舍：表越长，误拦可信目标的风险越高
- **不拦「公网 IP 但带内网路由」**：路由层面的事不该由应用层猜
- **不做 DNS 黑名单**：只判「这次连接实际拨的地址」，不维护域名名单
